## FIX-1 任务切面仍在搬运任务文件正文（装配超预算）

**现象**：契约装配时 `task` 段常驻约 2150 字符；除 `mandate` 外的片段合计约 2915~3256 字符，超过 `DESIGN.md` §5.2 的目标「除 mandate 外 ≤2500 字符」。根因是 `readTaskBrief` 把任务文件**截断到 2000 字**后仍塞进注入——本质还是"搬运正文"。

**涉及文件**：`src/contract/slices.js`（`readTaskBrief` / `searchDocs`）、`src/contract/assemble.js`（`SEGMENT_LIMITS`）

**修法**：
- 任务切面**只给**：`任务号` + `任务文件的绝对路径` + `上级补充指令（仅 delta）` + `config.project.brief` + `debug 文件清单`
- **删除任务文件正文摘录**（包括"截断到 N 字"的变体）——总纲第 4 条已要求子智能体自己去读任务文件
- `task` 段预算上限设为 **≤300 字符**

**验收（补测试）**：用一份 >5000 字符的任务文件做夹具，装配一次：
1. 装配文本里**不出现**该任务文件的正文片段（包括其尾部标记词）
2. 除 `mandate` 外合计 **≤2500 字符**

## FIX-7 面板把"已结算的后台成员"误判成一次性 → 默认过滤把它吃掉（应用内实测）

**现象**：会话里已有 `reviewer`（宿主 UI 显示**可继续 · 已完成**），但「契约」tab 仍显示「没有可显示的节点」。即：**非一次性成员也不显示**。

**根因（两重）**：
1. **mode 判定用了近似**：`src/client/tab.js` 中
   ```js
   if (info && (info.mode === 'one-shot' || info.mode === 'continuable')) return info.mode
   return row.agentAvailable === true ? 'continuable' : 'one-shot'
   ```
   已结算的 continuable 成员 `agentAvailable=false` → 被近似判成 `one-shot`；又因 `status=completed` 命中默认过滤 `hideDoneOneShot`（谓词本身正确：`one-shot && (completed||released)`）→ 被隐藏。
2. **过滤开关读回链路不可用**（3.3 既有未闭合项）：`pluginSettings[<tab id>]` 在 `TabComponentProps` 侧无公开 API → 用户即使去关开关**也可能无效**，于是"怎么都不显示"。

**涉及文件**：`src/client/tab.js`（mode 判定、空态渲染）、`src/panel/query.js`（如投影字段在此装配）

**修法**：
1. **mode 改用权威来源**：读 `subagentCatalog` 投影（`projections.values.subagentCatalog`），其 payload 记录 `mode: 'one-shot' | 'continuable' | 'unknown'`（fork 继承的 fact 已被排除）——与宿主自带 UI 显示"可继续/一次性"同源。**禁止**再用 `agentAvailable` 近似；投影缺失时保留 `unknown`（不要猜）
2. **空态自救入口**：面板无可显示节点时，渲染一句说明 + **「显示全部」按钮**（组件内部 override 过滤，不依赖 prefs 读回），让用户能立刻看到被默认开关隐藏的节点
3. `unknown` 模式：**默认可见**（宁多显示，不要静默隐藏）

**验收（补测试）**：
1. `settled continuable`（`agentAvailable=false` + `completed`）→ **默认可见**（本次事故的直接回归位）
2. `one-shot + completed` → 默认隐藏；关掉开关（或点「显示全部」）后可见
3. 投影缺失 → `mode='unknown'` 且默认可见
4. 空态文案与「显示全部」按钮存在，点击后树出现

## FIX-11 宿主与工作树版本漂移 → 运行时证据失真

**现象**：运行中的宿主加载的是**旧版插件**——运行时工具目录缺 `audit_scan` / `librarian_sweep` / `librarian_glossary` / `librarian_archive`（4 个在当前 `tools.js` 已注册）→ B 组全部运行时证据测的是旧版，结论失真。

**修法（两层）**：
1. **让"运行版本"可核对**：`contract_status` 输出 `pluginVersion` + **已注册工具清单**（或随快照写出）；核验前先比对"工作树 vs 运行中宿主"，不一致即标**未核验（版本漂移）**
2. 流程：改完代码**完整重启 DSH** 再跑运行时核验；核验报告须写明工具清单比对结果

**验收**：`contract_status` 能打印版本与工具清单，且与 `tools.js` 注册项一致（或明确列出差异）。

**★ 口径补充（2026-10-02 实测踩到）**：版本闸门的**期望值必须动态取自工作树的 `package.json` version**，**不得硬编码历史基准**——实现方会连续跳档（0.1.3 → 0.2.3），用旧基准会把"已同步"误判成"漂移"。
排查顺序：① 完整重启（托盘 Quit ≠ 关窗口）② 读工作树 version 与 `contract_status` 打印的版本对比 ③ 仍不一致 → 检查是否有第二个 app 实例 / link 是否存活 ④ 必要时重新 `add link:`。
**闸门只挡"运行时核验"，不挡改代码**：正确节奏是"改完一批 → 一次重启 → 一次核验"。

## FIX-12 面板「成员 0」：血缘根解析失败 + 空态文案误导（审查新发现）

**现象**：面板长期空。`成员 0` 出现在**过滤之前**的计数上 → 血缘树**从根上就是空的**（不是默认过滤吃掉的）。

**最小复现（审查方 vm 实测）**：
```
items=[]            → roots=0 members=0 → 空态        ← 与截图逐字吻合
items 不含 scope    → roots=0 members=0 → 空态
血缘正常(无投影)    → roots=1 members=2 → 过滤后 1 行
血缘正常(有投影)    → roots=1 members=2 → 过滤后 2 行
```

**根因**：`src/client/tab.js` 的 `rootOf()`（约 81-92 行）在 `items` 找不到当前 `sessionId` 时**原样返回 sessionId** → `subtreeOf()` 因 `byId.has(rootId)` 为假 → 返回 `[]` → 成员 0、空树。
**次因**：空态文案把"**数据源为空**"写成"当前过滤条件下没有可显示的节点"（约 447-450 行的更精确降级分支走不到），直接带偏排查方向。

**修法**：
1. `rootOf()` 加回退：`items` 不含 scope 时 → ① 用 scope 的已知祖先链 ② 否则取 `items` 中 `parentSessionId` 为空的顶层根 ③ 再不行用 scope 的全部后代（不要求 scope 在 items 里）
2. **空态三分类**：`数据源为空（remote 未返回会话列表）` / `过滤后无可见节点（可点「显示全部」）` / `加载失败（附错误）`
3. 断言：`items=[]` → "数据源为空"；`items` 不含 scope 但有后代 → **仍能渲染出树**；血缘正常 → 计数与树正确

**验收**：FIX-12 四个 vm 用例做回归；`items 不含 scope` 必须从 `roots=0` 变为 **`roots>=1`**。

## FIX-13 【critical】交集校验把宿主内建工具剔光 → 子智能体"能派活、不能干活"

**现象**：0.1.1 起通道"成功"启动，但子智能体只剩 3 个工具：`doc_emit` / `progress_upsert` / `subagent`。
实测（implementer 与 reviewer 独立复现）：
```
pwsh → Error: unknown tool "pwsh"
read / glob / grep / write / edit / todo_write → 全部 unknown tool
契约声明有、实际没有：read、write、edit、glob、grep、pwsh、bash、todo_write（共 8 个）
```
后果比修复前更糟：修复前是**可见的 start 报错**；现在是**静默降级**——研究员读不到档、实现者写不了代码、审查者读不到源码。

**根因**：`resolveToolFilter()` 把 `ctx.tools.schemas()` 当成"宿主工具目录"，但**在插件自己的上下文里，它只枚举到本插件注册的 13 个工具**。于是 8 个宿主内建工具全被判定"未注册"而剔除，`allow` 只剩 `doc_emit`/`progress_upsert`，宿主再附 `subagent`。
佐证：implementer 声明 8 个、reviewer 声明 3 个，**剔除后都只剩同样 3 个**，剔除量恰好等于各自声明里的宿主内建工具数——不是名字写错，是**枚举面选错**。

**为什么套件照不到**：`verify.mjs` 的 `HOST_TOOL_CATALOGUE` 是**手写 fixture 塞进 `ctx.tools.schemas`** → OK 45 永远为真。**fixture 撒谎**。

**修法（按可靠性排序）**：
1. **改为 fail-open 默认**：不做存在性剔除，声明的名字**原样下发**；只在能拿到**权威**宿主工具目录时才校验（且必须写明该目录的来源与可信理由）
2. **平台解析代替存在性校验**：终端工具用互斥对时，在本地按平台**解析成单个正确名字**（win32 → `pwsh`，其他 → `bash`），而不是靠剔除
3. **删除/降级假目录**：不得再把 `ctx.tools.schemas()` 当宿主目录；若保留该调用，必须标注它只覆盖本插件注册面
4. **warning 必须可见**：委派回执的 `render` 要渲染 `warnings`（当前只打印"已派出…契约 N 字"），否则"已剔除：read、write…"上级根本看不到

**验收（补测试，且**不许**再用假目录糊过去）**：
1. 回归位：**空/不完整的工具目录下，不得剔除任何声明名**（fail-open），断言 `allow === 声明名（经平台解析后）`
2. 平台解析：win32 → `pwsh` 且**不含** `bash`；非 win32 → 反之
3. 回执渲染：`warnings` 非空时，`render` 输出里必须能看到这些 warning
4. 删除或改写 `HOST_TOOL_CATALOGUE` fixture，使其**不再暗示**"这是宿主全量目录"

## FIX-14 【minor】快照没读被写成"对方没写"（误导排查）

**现象**：面板底部显示「三档 / 进度 / 预算 徽章：数据源待接（**对方未写出派生快照** .agent-contract/panel.json）」——但 `panel.json` **确实已写出**（B1 已证：2274 bytes）。

**根因**：`items` 为空 ⇒ `rootRow` 找不到 ⇒ `rootCwd` 空 ⇒ `loadPanelSnapshot` 在 `!rootCwd` 处**直接 return null，根本没去读那个文件**。**"没读"被写成了"对方没写"**，把锅甩给了 host。

**修法**：
1. 分清两类：`未能定位项目根（血缘为空）→ 未尝试读取` vs `已尝试读取但文件不存在`（后者才叫"未写出"）
2. `rootCwd` 拿不到时给出**回退**：用 scope 会话自身的 `cwd`，或用配置里的 `project.root`

**验收**：`rootCwd` 空 → 文案含"**未能定位项目根**"且**不含**"对方未写出"；正常路径 → 能真读到快照并贴徽章真值。

## FIX-16 【critical】用 `props.ctx` 访问 remote → `cannot get property "remote.workspaceFiles" without inject`（重启后实测）

```js

// tab.js:376
```

```js
ctx.inject(['remote', 'remote.officeToPdf', 'remote.workspaceFiles'], (scope) => {
```

**验收（补测试）**：
1. 模拟"`props.ctx` 上没有 `remote.workspaceFiles`、而注入 ctx 上有" → **仍能读到快照**（不得 failed）
2. 血缘读取失败与快照读取失败的 reason 文案**不同**且各自指向正确步骤
3. 回归：`inject` 数组仍含 `remote`/`remote.session`/`remote.workspaceFiles`

## FIX-19 【critical】任务号含下划线时，改名会重复前置任务号（= 报告里的 FIX-29，**已污染项目文件**）

**现象**：一轮馆员治理把 4 篇文档改名成**任务号拼两遍**：
```
T99_契约流程冒烟测试_T99-冒烟测试审查者通道回报-高度概括_L3.md
```

## FIX-39 【设计】面板数据不该由"审计"驱动 —— 待办/成员视图必须随状态变化自动更新

**用户问出来的问题**：「为什么待做任务列表是审计来管理的？」——问到点子上了。

**现状与成因**：面板读的 `panel.json`，其**重写时机只挂在两点**：① 审计跑完（`audit_scan`）② 台账批次边界（`ledger_rebuild`）。待做清单（未结任务 + 缺失产出 + 审计红黄）是后来塞进同一份文件的 → 形成"**想看待办得先跑一次审计**"的别扭因果。用户实测：插件升级后面板一直显"陈旧"，唯一出路是"让主代理跑一次审计"。

**为什么别扭**：待办/成员是**面板视图**（项目状态的呈现），审计是**其中一类数据来源**——两者不是因果关系。

**要求（只讲性质，不讲做法）**：
1. 面板数据（成员 / 待办 / 审计摘要）应**随项目实际变化自行更新**——用户**不需要**为了看到新数据而先跑一次审计
2. 更新要**及时但不频繁**：短时间大量变化不应造成频繁重写
3. **审计只是数据来源之一**，不再是刷新面板的唯一入口
4. 面板侧原有的读 / 轮询 / 手动刷新保留，但"刷了也没新数据"这种体验不应再出现

**验收**：① **不跑任何审计**，只派一个子智能体 / 只让某个成员用 `doc_emit` 落一篇档 → 面板的成员数与待办在 **≤30s 内自行更新**；② 跑审计仍照常更新；③ 节流生效（短时间大量变更不产生频繁重写）；④ 快照写入不再是"必须人工触发"的动作。

## FIX-45 【高】勾选时误报"文件已被外部改动"（假冲突 409）→ A 区写通道在真机不可用

**现象（真机）**：点任一复选框 → 提示「⚠ 文件已被外部改动 → 已拒绝本次写入，请刷新后重试」。但 `待办.md` 自 **2026-08-17** 起 mtime/sha 未变（`00B6EA878E10`）——**从来没有外部改动**，是**假阳性**。

**已排除（dsh 实测四组）**：① 两侧哈希算法不一致（6 组取样逐位一致）② BOM（文件头 `23 20 42`，无 BOM）③ 把 80 行预览当全文（`baseHash` 取的是全文）④ 白名单误判（合法路径拿到的是 409 不是 403）。

**收窄后的结论**：冲突比的是「**client 读到的文本**」vs「**宿主 `readFile` 读到的文本**」⇒ 二者必然不同，即 `remote.workspaceFiles.read` 的返回与宿主直读**不一致**（长度 / 换行 / BOM / 截断之一）。**根因未最终定位**（无法从宿主侧观测 client 那次读）。

**修法（先可诊断，再治本）**：
1. **409 响应必须回带宿主的实际值**：`actualHash` + `actualLength`（可选 `actualHead` 前若干字节）—— 一次对比即可定位这类"两侧读法不同"，不必再开实验
2. **治本：读取与哈希同源**——面板的待办读取也走**宿主那条读路径**（同一条路由的 GET），client 只负责显示；一处读、一处算哈希，从结构上消除"两边读法不同"
3. 备选（若 2 代价大）：冲突校验退成**行级**——只校验"将被翻转的那一行"的原文，而不是整文件哈希（与"行级翻转"的语义一致）

**验收**：① 文件未变时点复选框 → **写入成功**（不再 409）；② 人为制造"外部改过"（改内容或改 hash）→ 仍正确报 409；③ 409 响应含 `actualHash` 与长度；④ 越权路径仍 403、GET 仍 405。

## FIX-47 【口径】FIX-39 验收修正 + 成员树低频整轮重载

**实测事实（dsh）**：FIX-39 机制**生效**（派子智能体后 **2.2 秒**快照更新、审计块**沿用并标 asOf**、没归零）；但 **`待办` 更新了、面板"成员 N"没更新** —— 因为轮询走的是"**只重读快照**"（刻意不重拉 `remote.session.list` + 逐会话投影，那最多 20 个请求），而成员数显示的是**会话血缘树**。

**修法**：
1. **低频整轮重载**：轮询时每隔若干次（如每 3 次 ≈ 60 秒）做一次**整轮重载**（血缘 + 快照），其余只重读快照 → 成员树/成员数最坏 ~60 秒跟上，同时不打爆 remote
2. **验收口径改准**（避免再拿单一数字验收）：
   - 待办 / 审计摘要 / 成员徽章：随快照更新，最坏 ≈（宿主 2s + 轮询 20s）**≈22 秒**
   - **成员树结构**（含"成员 N"计数）：最坏 **≈60 秒**（低频整轮重载），或用户点「↻ 刷新」立即
3. 可选（体验）：面板显示"数据截至 `<asOf>`"，让用户一眼知道新旧

**验收**：① 不跑审计、只派一个子智能体 → **≤60 秒**内成员数也自行变化；② 待办/徽章 ≤22 秒；③ 轮询仍以"只重读快照"为主（整轮重载是低频）；④ 断言含 `PANEL_FULL_RELOAD_EVERY`（或同义常量）与轮询计数逻辑。

## FIX-48 【瘦身】文档切片不该附"引文"（实测一次装配塞 5 篇 ≈1200 字符噪声）

**现象（用户贴的真机实例）**：一次派单的契约里，"文档切片"段附了 **5 篇文档 ×（路径 + 命中原因 + readHints + ≤200 字符引文）** ≈ **1200 字符**，而召回的 5 篇（`^电力系统`、`^研究-传送带物品方向`、`^研究-核心染色修复`…）与该任务（工具探针）**基本无关**。

**根因**：`slices.js:169` —— `if (hitReason.length >= 2) entry.excerpt = raw.slice(0, cap)`：只要"实词命中 ≥2"就附引文，而这 2 个命中里常是泛词/项目名（见 FIX-50），于是**低相关文档也带引文**。

**修法**：
1. **默认不附引文**（切片只给：路径 + 一句相关性说明 + readHints）；需要内容时让子代理按 readHints 自己去 `read`（这正是"禁搬运"纪律）
2. 若保留例外通道，条件收紧为：**强信号词命中**（非泛词、非项目名、非英文通用词）**且**该片的命中强于其它片（如 Top-1/Top-2）
3. **切片段单独设字数上限**（如 ≤1200 字符；超出只留路径 + readHints），避免"文档一多就挤掉正事"

**验收**：① 低相关召回**不带引文**；② 高相关（强信号词）至多 1~2 篇带引文且 ≤200 字符；③ 切片段总长 ≤ 上限；④ 契约总长显著下降（同任务对比，至少 −800 字符）。

## FIX-50 【质量】命中原因要可读 + 停用词补英文通用词与项目名

**现象（同一实例）**：文档切片的「命中原因」是 `write、工具、实际、blockdustry` 这类——**泛词 + 英文通用词 + 项目名**，对"这篇跟我有关吗"几乎零信息量；`blockdustry` 几乎每篇文档都出现，却仍被当作命中原因。

## FIX-51 【体验·反复踩】插件升级后快照不自动刷新 → 面板显示"数据源待接 / 未读到：未知原因"

**现象（面板截图，真机）**：
```
▾ 待办任务（大方向）  [编辑]
    待办原文未读到：未知原因
▾ agent 待办（执行队列）
    数据源待接：快照由旧版插件（0.4.0）写入，当前 0.4.1
```
**这是一个原因的两个表现**：快照是 **0.4.0** 写的，**0.4.1** 的客户端按 FIX-36 判定它**陈旧** → 拒绝使用其字段（含 `paths.todoFile`）→ A 区拿不到路径。

**两个真问题**：
1. **升级后没有任何"自动重写快照"的机制**：`snapshot-sync.js` 只在"文档/任务/成员记录变化"时重写；`snapshot.js` 只是把 `pluginVersion` 写进去。于是**每次插件升级后**面板都停在"数据源待接"，要么等用户碰巧做了个动作，要么手动跑一次审计——**这个坑已经踩到第三次**（0.3.3→0.3.4、0.4.0、0.4.0→0.4.1）。
2. **A 区的"未知原因"其实是"没尝试读"**：`tab.js:1890` 的 effect 在 `!todoPath` 时**直接 return**，从未设置 `todoReason` → 渲染出 `todoReason || '未知原因'`（`tab.js:2060`）。**把"没读"写成"未知原因"**，与 FIX-14 是同一类错误（把"没做"说成"对方没写"）。

**修法**：
1. **启动即自愈**：插件初始化时（或首次生成快照的时机）比较"现有快照的 `pluginVersion`"与"当前插件版本"，**不一致就直接重写一次快照** —— 用户不需要做任何事
2. **A 区失败原因必须具体**：`!todoPath` 那条早退路径也要**设置原因**（如「快照陈旧，未提供待办文件路径」/「快照未生成」），**禁止出现"未知原因"**；渲染文案里"未知原因"这个兜底只留给真正的意外异常，并附上可诊断信息
3. （与 FIX-45 的修法 2 联动）读取与哈希同源后，A 区的读失败也应给出宿主侧的具体原因

**验收**：① 人为把快照的 `pluginVersion` 改旧（或升级插件后重启）→ 面板**不需要任何人工动作**即在数秒内恢复显示真值；② 陈旧/无路径场景下 A 区文案**含具体原因**、**不含"未知原因"**；③ 正常场景不受影响。

## FIX-53 【阻断·真机】`settings is not defined`：组件跨作用域抓变量 → client 整块崩

```
src/client/tab.js:1761   badgeCell(item.key, item.value, settings.badgeLabels)   ← 用了 settings
```

## FIX-55 【高·影响异源】设置页 JSON 只显示"覆盖层"，看不出生效值；且"空对象"可能抹掉配置文件的值

1. **误导**：用户看到 `modelRoutes: {}` 会以为没配（实际生效的是配置文件里的值）
2. **可能抹掉**：若宿主表单是**整对象覆盖**语义，把这份空 `modelRoutes` 保存下去会**覆盖掉配置文件的 `adversary`** ⇒ 异源**静默失效**（M5 会验不出来"真对抗"）

2. **写入语义写死为"缺键 = 继承"**：设置页的空对象/缺键**不得**覆盖配置文件的值；需要清除覆盖时走显式的「恢复默认」按钮；若宿主是整对象覆盖，则插件侧必须先**深合并**再写
3. **模型名可改**（用户核心诉求）：在设置页改 `modelRoutes.adversary` 的值必须**真生效**（下次派单即用新模型）

**验收（受控实验，M5 之前必须做）**：

## FIX-56 【高】设置页开关写入被宿主拒绝（"宿主返回 false"）—— 写的是叶子路径，契约要的是"一个字段"

**现象（真机）**：在设置页切「隐藏已完成的一次性节点 = false」→
```
✗ 宿主拒绝了这次写入：隐藏已完成的一次性节点 = false
宿主原话：宿主返回 false（未接受这次写入）
```
（注：插件 Config **已声明**该字段，`index.js:72 hideDoneOneShot: Schema.boolean().default(true)`，不是"字段没声明"。）

**根因（宿主契约 vs 我们的写法不一致）**：
宿主 `packages/client/ui-settings/src/client/config-form.ts`：
```ts
/** @param field - scalar field inside the namespace section. */
set(field: string, value: unknown): Promise<boolean> {
  return this.mutate([{ op: 'set', path: [field], value }])      // ← 单层：命名空间下的【一个字段】
}
mutate(ops, expectedRevision?): Promise<boolean> {
  const revision = expectedRevision ?? this.pendingRevision ?? this.getSnapshot().revision   // ← 乐观并发
  const response = await this.ctx.remote.settings.mutate(this.spec.namespace, ownedOps, revision)
  if (!response.ok) { await this.recover(generation); return false }   // ← 这就是"返回 false"的来源
}
private enqueue(op) { if (this.persistence === 'memory' || this.disposed) return Promise.resolve(false) }
```
而插件侧：`src/client/tab.js:2546`
```js
Object.entries(patch).map(([key, value]) => ({ op: 'set', path: ['panel', key], value }))   // ✗ 两层叶子
```
⇒ **契约要"写一个字段"（`path: ['panel']` + 整个 panel 对象），我们写成了"写叶子"（`['panel','hideDoneOneShot']`）** → 宿主不接受。
（旁证：设置页的「调用 JSON」写入走的是顶层 `['modelRoutes']` / `['panel']` —— 形状对；两处写法不一致正是问题来源。也解释了 CC 注释里说"写的是 panel 整个对象"而代码是叶子。）

**修法**：
1. **统一成"写字段"**：面板开关写入改为 `{ op:'set', path:['panel'], value: <合并后的完整 panel 对象> }`（与 JSON 编辑区同一条写路径、同一形状）
2. **revision 语义**：写失败时按宿主契约处理——`mutate` 内部会 `recover()` 重载；插件侧应**读取重载后的值再重试一次**，不要连续盲写
3. **诊断可见**：`mutate` 只返回 boolean；需要原因时**直接调底层** `ctx.remote.settings.mutate(ns, ops, revision)`（范例 `ui-settings-models/src/client/operations.ts:97`），把 `response.ok`/错误内容带进面板提示（别再只说"宿主返回 false"）
4. 顺带核查：`persistence === 'memory'` 时宿主一律返回 false（宿主行为），若命中要给出"当前会话不可持久化"的明确提示

**★ 裁决（2026-10-03）：选 B（官方 volatile 形态）** —— 理由是"设置页能改模型名"是用户的原始需求，而它**只有这一条通路**；代价只是文档口径改一句。附四条护栏：

1. **默认值搬进 schema**（如 `modelRoutes.adversary` 的默认 `glm-5.3-flash`、五项开关的默认值）；`cordis.patch.yml` 里对应键**要么删除、要么明确标注"由设置页管理（volatile），此处改了不生效（仅示例）"** —— **不允许出现"文件里写了值、实际不生效、又没有任何标注"**
2. **空对象/缺键 = 继承默认**（这条是 FIX-55 的核心）：用户把 `modelRoutes` 写成 `{{}}` 时**不得**让 `adversary` 丢失（否则异源静默失效、M5 会验不出来）；插件侧取值时按 `{{...默认, ...用户值}}` 合并，或在关键键（adversary）上做兜底
3. **"只解析一次"钉断言**：volatile 投影后的值再进 schema 会抛错 → 加载路径不得二次解析
4. **密钥红线不变**：volatile 的 `modelRoutes` 里**只放模型名/路由参数**；key 永远在宿主 provider 账户

**文档同步（B 的代价，必须一起改）**：`README` 与 `DESIGN §5.6` 的 FIX-52 ⑤ 口径从"设置页覆盖配置文件"改为「**这些键由设置页管理（volatile）；配置文件里只作示例/说明**」，并**分别列出**：由设置页管理的键（modelRoutes / panel 五项）与仍归配置文件的键（paths / audit 阈值 / budgets）。

**验收**：① 切「隐藏已完成的一次性节点」→ **写入被接受**（true）、面板立即生效、**重启后保持**；② 写入用的 ops 形状与 JSON 编辑区一致（顶层字段）；③ 失败时提示**含具体原因**（不是"宿主返回 false"）；④ 非法值（如 `pollSeconds: 'abc'`）仍被拒且原因可见。

- **缺失的通用纪律**（当前角色卡没有，或只散在代码里）：写下前先出 dryRun 预演；判不准一律上报（不许猜）；移动/改名后同步更新引用；覆盖旧版本前留备份；改动必须留痕（`librarianTouchedAt`/`librarianChanges`）；归档的边界（什么进 archive）。

**要求**：
1. **重写 librarian 的 persona / forbidden / deliverable**，覆盖上述通用纪律（明确写"这些是准则，任务单无需重复"）；删掉"M2 只做两件事"这类**阶段快照**表述，改为**当前完整职责**（巡检直修 / 回填 / 归档 / 一轮治理 / 术语表 / 关键词复核 / 归位建议）
2. 若某条纪律**已经由代码强制**（写前备份 `writeWithBackup`、留痕、正文零改动），角色卡里写"已由工具强制，无需你操心"，避免子代理重复设防
3. **加一条防漂移**：角色卡不得出现"本阶段只做 N 件事"式的**实现阶段描述**（阶段会过时）；职责用"能力"表述
4. 断言：角色卡文本包含上述通用纪律关键词（dryRun 预演 / 判不准上报 / 引用同步 / 备份 / 留痕），且**不含**"只做两件事"这类过时表述；改完 `grep` 可检索

**验收**：① 馆员角色卡与当前工具集/职责一致；② 通用纪律齐备且可被断言检索；③ 不出现阶段快照式表述；④ 任务单只需写"范围 + 本次特有约束 + 验收"，不必再抄纪律。

## FIX-61 【体验】探测到"项目结构缺失"时要主动提示，不要让用户自己记得去调 project_init

**背景**：FIX-58 落地后，探测是自动的、但**建目录只有 `project_init` 会做**，而插件**不会主动提示**这件事（代码里没有任何"结构缺失→建议初始化"的输出）。于是：
- 用户不知道要叫它（本次就出现了：「让主代理调 project_init 是什么意思，我要写在提示词吗」）
- 主代理也未必想到去调（工具描述里有说明，但没有"当前结构不全"的信号触发它）

**要求**：
1. **派生一条状态**：解析出的项目里，若"默认结构该有的目录 / 待办文件"缺失 → 在 `contract_status`、派单回执、与面板上给**一句明确提示**（例如「本工作区尚未初始化：缺少 任务/、[Agent进度]、docs/… —— 调 `project_init` 可预览并建齐（只新建、不覆盖）」）
2. **提示要可关**：项目已完整、或用户已显式初始化过（`project.json` 存在且结构齐）→ 不再提示（别变成常驻噪音）
3. 只**提示**，不自动建目录（建目录仍是显式动作，符合"只新建需人点头"的既有纪律）

**验收**：① 全新空文件夹当工作区 → `contract_status` / 派单回执里出现"尚未初始化 + 建议调 project_init"的提示；② 已初始化（Blockdustry 那种）→ **不出现**该提示；③ 提示文案含 `project_init` 且说明"只新建、不覆盖"。

## FIX-62 【体验】会动真实文件的任务，派单时要提示"先提交一次 git 基线"（只提示，不自动提交）

**背景（用户提问）**：用户希望「只跟主代理说一句『按照规则整理文档』，它就**先 git 一次**，再派馆员整理，再确认格式」。
实测缺口：插件里**完全没有 git 相关能力或纪律**（`grep` 全仓：只有注释/EXECUTOR-RULES 提到 git，运行期无任何提示）⇒ 主代理会不会先提交基线，纯看它自己想到没有。

**要求**：
1. **只提示，绝不自动提交**：插件不执行 `git`（提交是外向、有副作用的动作，静默做很危险）
2. **提示出现在**：涉及文件变更的角色（librarian / implementer 等）派单的**回执**里，以及该任务的首个写动作被调用前（如 `librarian_sweep` / `doc_emit` 非 dryRun 时）
3. **提示要具体**：若项目根是 git 仓库且有未提交改动 → 「建议先提交一次基线：当前有 N 个未提交改动（`git status --short`）」；若不是 git 仓库 → 不提示（别噪音）
4. **不硬拦**：提示归提示，用户/主代理可以选择不提交（既有"警告制"口径）
5. **只读探测的加固**：只允许**只读子命令白名单**（`git status --porcelain` / `git rev-parse` 之类，**不含任何写类子命令**）；探测**带超时**（如 2 秒），**失败/超时/git 不存在 → 静默降级**（跳过这条提示，不报错、不阻断工具调用）；每次派单或首次写动作前**最多探测一次**（不要每步都调）

**口径澄清（2026-10-03，用户提问后裁定）**：本单原验收④写作「插件**不执行任何 git 命令**（源码无 child_process 调 git 的路径）」——这与 FIX-67（自动提交必须调 git）及本单要求"报出 N 个未提交改动"（必须读 `git status`）**互斥**，是起草时写死过严。现改口径为：**只读探测允许；写类命令（`add`/`commit`/`tag`）仅在 `git.autoCommit` 打开时执行；任何情况下不得 `git push`**。**这是口径澄清/修正，不是放宽**（原口径实际上不可能同时满足三条要求）。

**验收**：① git 仓库 + 有未提交改动时，派单回执/首次写动作前出现具体提示（含改动数）；② 干净工作区 → 不出现该提示；③ 非 git 仓库 → 不出现；④ **默认路径（`git.autoCommit` 未开）零写类 git 调用**，且**源码中不存在任何 `git push` 路径**；⑤ 只读探测的 git 子命令**都在白名单内**（断言可检查子命令集合）；⑥ git 不存在 / 超时 → 静默降级、不阻断。

## FIX-63 【架构】工具面缺角色闸门：主代理能直接调馆员的工具 → "空着的椅子"被坐上去

**来源（dsh 主代理的反思，原话）**：「工具面没有闸门。`librarian_sweep` / `librarian_archive` / `librarian_patrol` 这些工具直接暴露给我，描述写的是『图书管理员的归档动作』，但没有一条写『主代理不得直调、必须委派』。整个契约里唯一相关的硬约束是馆员角色卡的『禁止自行派单（馆员不派活）』——它管的是馆员别派活，没管主代理别干活。我照字面读，唯一空着的椅子就是执行者，于是我坐了上去。」

**问题本质**：按本插件架构，"整理 / 归档 / 命名规范化"这类活**属于馆员**（因为馆员角色卡携带纪律：dryRun 先行、判不准上报、引用同步、留痕）。但**工具面对主代理完全敞开**，于是：
- 主代理直调 `librarian_*` → 绕过馆员角色卡的全部纪律
- 且**没有任何一条机制**表达"这活该由谁干"——纪律只在**角色卡文本**里，不在**工具门**上

**修法**：
1. **工具描述明写归属**：`librarian_*` / `ledger_backfill` 等馆员作业面工具的描述里，加一句「**该工具面向图书管理员角色；主代理应通过 `contract_delegate_librarian` 委派，不得直调**」
2. **主代理直调 → 回执带明确警告**：检测调用方身份（解析调用者角色/层数）→ 若是主代理（层 0）→ 结果里附一条 `警告：这是图书管理员的作业面；请改用 contract_delegate_librarian 委派（直调会绕过馆员角色卡的纪律与留痕口径）`
3. **可选严格模式**：配置项（如 `delegation.strictRoleGate: true`）下，主代理直调馆员工具 → **直接拒绝**并给出正确姿势；默认仍是"警告制"（与整体口径一致）
4. **断言**：① 工具描述含归属句；② 主代理直调时回执含该警告（身份可解析时）；③ 严格模式下被拒；④ 馆员自己调用**不受影响**（不能把馆员自己的路堵死）

**验收**：真机让主代理直调 `librarian_sweep` → 回执出现"该由馆员执行/请委派"的警告（严格模式则为拒绝）；馆员经委派调用正常。

**验收**：① 插件给出作业登记卡模板（必备字段齐备）；② 交付时缺必备字段 → 有提示；③ 字段齐全 → 无提示；④ 文档写明"任务文件 = 子代理作业登记卡"；⑤ 断言可 grep 到模板与校验实现。

## FIX-65 【体验】面板"自动刷新很慢"：轮询 20 秒 + 页面切回来要再等一拍

**用户反馈**：「插件列表显示的是最新版的了，但是契约面板自动刷新很慢」。

**实测现状（代码 + 盘上数据）**：
- `PANEL_POLL_MS = 20_000`（20 秒）⇒ 宿主动作后，新数据最坏 **≈22 秒**（宿主 2s + 轮询 20s）才出现在面板上
- `shouldPoll(doc) = !(doc.hidden)` ⇒ **页面隐藏时暂停轮询**，且**没有 `visibilitychange` 监听** ⇒ 窗口切回来那一拍还没到，用户要再等最多 20 秒 = 体感"很久都不动"
- `PANEL_FULL_RELOAD_EVERY = 3` ⇒ 成员树要 **≈60 秒**才跟上
- （顺带确认：重启后快照已由 **0.9.0** 写出，之前的 0.8.2 是重启前那份 ✓）

**修法（体感提速三件套）**：
1. **轮询 20 秒 → 5 秒**：这条路径**只重读快照文件**（十几 KB），5 秒一次成本可忽略；断言下限仍是 ≥5000ms（不越界）
2. **页面重新可见时立刻刷一次**：监听 `visibilitychange`，从隐藏变可见 → **马上** poll 一次（不等下一拍）；隐藏期间仍暂停（保 FIX-38 的"别白烧 IO"）
3. **整轮重载（血缘 + 快照，最贵的一步）改为每 30 秒**一次（在 5s 拍长下 = 每 6 拍），把成员树的最坏延迟从 60s 压到 ~30s；仍**不得**跟着 5s 拍走（那会频繁重拉 session 列表与投影）

**验收**：① `PANEL_POLL_MS` 为 5000（且断言仍含"≥5000"下限）；② 存在 `visibilitychange` 处理，且**可见时立即触发一次 poll**；③ 整轮重载节拍为 30 秒（常量可断言、纯函数 `nextPollMode` 仍可单测）；④ 隐藏时跳过轮询的行为**保留**；⑤ 面板「最后更新」时间随刷新可见（tooltip 已有，确认仍生效）。

## FIX-66 【机制】治理类任务完成后，验收报告由插件自动产出（不要靠人手工对）

**用户批评**：「这些约束应该是插件提供的」——任务单里写着"正文零改动（逐篇 sha 一致）""引用无失效""审计红黄数 ≤ 基线""报告格式：移动 X 篇 / 改名 Y 篇 / 更新引用 Z 处 / 待人工裁定 N 篇"。这些**插件全都有数据**（改动清单、文件指纹、引用、审计前后），却让主代理/人去手工核对——正是"该自动化的没自动化"。

**要求**：`librarian_sweep`（一轮治理）与 `librarian_archive` 等治理动作**结束时自动产出一份验收报告**，至少含：
1. **动作清单**：移动 X 篇 / 改名 Y 篇 / 更新引用 Z 处 / 归档 N 篇 / 待人工裁定 M 篇（**每条带绝对路径与原因**）
2. **正文零改动证明**：逐篇"动手前指纹 → 动手后指纹"，**不一致的单独列出**（工具只动元数据/命名/位置的承诺，用数据证明）
3. **引用完整性**：改名/移位的目标，全库检索**是否仍有旧路径残留**（有则列出）
4. **审计前后对比**：`audit_scan` 的 红/黄 计数与条目 diff（治理前 vs 治理后）
5. **`dryRun` 也要给同一份报告的预演版**（"将移动 X / 将改名 Y / 将删除引用 Z"）

**验收**：① 真机跑一轮治理 → 报告自动出现且上述五项齐备；② 报告里的"正文零改动"逐篇给出前后指纹；③ 故意制造一处"改了正文"→ 报告必须点出来；④ 引用残留能被检出；⑤ `dryRun` 给预演版。

## FIX-67 【可选】自动 git 提交：默认关闭 + 范围护栏（用户问"没有自动 git 提交吗"）

**背景**：用户问「没有自动 git 提交吗」。FIX-62 的设计是**只提示不提交**（提交是外向写操作、可能把用户 WIP 一起提交、author/范围/信息都要判断）。用户既已明确想要自动化，则提供**带护栏的可选开关**，而不是直接拒绝。

**要求**：
1. **默认关闭**：新增配置项 `git.autoCommit`（默认 `false`）；关闭时行为 = FIX-62 的"只提示"
2. **打开后的护栏（缺一不可）**：
   - **只暂存本次动到的路径**：`git add -- <本次动作清单里的绝对路径>`（精确 pathspec，**绝不 `git add -A`**）
   - **提交前检查范围**：若工作区存在**本次范围之外**的改动（未提交的别的文件）→ **中止提交**并提示"工作区有范围外改动，已跳过自动提交（避免把你的 WIP 一起提交）"
   - **提交信息**自动生成且可追溯：形如 `[agent-contract] <任务号>：<动作摘要>（移动 X / 改名 Y / 归档 Z），备份见 .agent-contract/backups/<时间戳>`
   - **可选打 tag**：`git.autoTag`（默认 false）打开时，提交前创建锚点 tag（如 `agent-contract/<任务号>-before`）便于整体回退
   - **失败必须明说**：git 缺失 / 非仓库 / 提交失败 → 明示原因，**不静默**（且不得阻断治理动作本身）
3. **不自动 push**：任何情况下不执行 `git push`（推远端需要用户授权）
4. **原子性**：一次治理动作 = 最多一次提交（不要逐文件提交）

**验收**：① 默认关闭时**不发生任何 git 写类命令**（只读 `status` 探测除外，见 FIX-62 的口径澄清）；② 打开后：只提交本次动到的路径、信息含任务号、其余改动保持未暂存；③ 工作区有范围外改动时**中止并提示**；④ git 不存在/非仓库时明示且不阻断治理；⑤ 断言：源码中**没有** `git add -A` / `git push` 的调用路径；写类子命令仅在 `autoCommit` 打开时可达（断言可检查调用点被开关包住）。

## FIX-68 【机制】把「占用文件/资源」用起来：并发占用冲突审计

**背景**：任务卡里的 `占用文件/资源` 段（55 张卡里 50 张都有）现在**只是文字**——写着"谁在用哪些文件"，但**没有任何机制读它**。它本来是用防冲突的手工纪律（多代理并行时避免互相踩），完全可以机制化。

**要求**：
1. **解析**：把任务卡 `占用文件/资源` 段解析成机读数据 `{taskId, path, mode: read|write|newFile|forbidden}`（路径归一化：绝对路径、去引号、Windows 反斜杠统一）
2. **冲突判定（审计项，警告制）**：

## FIX-80 【机制】写文件不得改动行尾 —— 否则每轮治理都制造几百处"假差异"，把 git 基线对账搞脏

**真机实证（2026-10-03，回滚之后）**：
```
工作区 ^修改-钻头侧面贴图应用.md : CRLF 47/47（全 CRLF）   HEAD : CRLF 0（全 LF）
工作区 P2_...设计v1.md          : CRLF 169/169               HEAD : CRLF 0
git diff --ignore-cr-at-eol  → 改动文件数 0（整仓）
git status                   → 397 处 M（docs 180 处），--stat 报 16714 插入 / 16714 删除
```
⇒ **内容已完全回到基线**，但**行尾被整篇改写**（LF → CRLF）。因为 `core.autocrlf=false` 且 `.gitattributes` 只覆盖 `src/generated/**`，
git 把每一行都算成"删一行 + 加一行" ⇒ 假差异淹没真实改动，**"与开工前 git 基线对账"这条验收直接失效**（分不清"真改了内容"还是"只是行尾"）。

**要求**：
1. **写入保持原文行尾**（核心）：凡是"读改写"既有文件的路径（`librarian_sweep` 改名/头部补写、引用修正、搬移后回写、`mergeIndexBlock` 等）——
   **读进来是什么行尾，写出去就是什么行尾**；原文混用行尾时**逐行保持**，不得整体归一化为 `\r\n`
2. **新建文件用 LF**（与仓库既有 .md 现状一致；如仓库另有约定，以配置为准）——新文件用 CRLF 同样会制造后续假差异
3. **审计/验收里加"行尾不变"这一条**：治理类动作结束后的验收报告（FIX-66）里，若某文件"内容相同但行尾变了"→ **单独列出**并提示"行尾被改写（非内容改动，但会污染 git 基线对账）"
4. **断言**：① 对 LF 文件的读改写往返后仍为 LF（含混用行尾的样本）；② 新建档为 LF；③ 验收报告能识别"仅行尾变化"

**验收**：真机对一批 LF 文档跑一轮治理（改名 + 头部补写 + 引用修正）→ `git diff --ignore-cr-at-eol` 仍能列出**真实**改动，而 `git diff`（不忽略行尾）**不再出现成百上千行"假差异"**。

（`仓库\docs\产出\T2_雷光特效_整合清单.md`、`T11…`、`T12…` 一长串）——用户感叹"librarian 确实够累的"。
抽一件事实：**索引需要的几乎全是机读信息**（路径 / 档级 / 任务号 / 标题 / 字数 / 关键词 / `relatedFiles` / 归档状态 / legacy），
这些**派生器早就算过并写进台账**（`deriveFromFile`，零模型调用）；它却靠"读全文"重建一遍 ⇒ 白烧一到两个数量级的上下文。
而且工具面上**没有**"一次拿全部档元数据"的只读入口（现有 `doc_search` 是检索、`librarian_*` 是动作）。

**要求**：
1. **新增只读工具（如 `doc_census`）**：一次返回全部档的机读元数据（同上字段），数据源 = 台账的派生记录；
   支持按类别 / 档级 / 任务号 / 是否有 legacy 过滤；输出**紧凑表格**（不要每篇一段散文）
2. **纪律写进角色卡与契约**：
   - 「**建索引、核对引用、统计这类工作不要读全文** —— 先 `doc_census`；确实需要正文时**优先 `doc_search` + 只读头部/速览**」
   - 「**索引的机器部分交给派生器**（`派生态索引.md` 的机器区块由插件生成）；你只处理 `needsLibrarian` / 待裁定项」
3. **读档要有上限意识**：需要看正文时，**先读头部（front-matter + 首屏 ≤3 行速览）**，确认必要再整篇读；
   连续整篇读超过 N 篇（如 5 篇）应**先回报"是否需要继续"**（避免一路读到底）
4. 断言：① `doc_census` 存在且返回机读字段（含 `legacy` / `archived` / 指针字段）；② 角色卡/契约含"不要读全文"与"先 doc_census"；
   ③ 过滤参数生效（按类别 / legacy）

**验收**：真机派一次"建索引/核对"类任务 → 它**先调 `doc_census`**（一两次调用拿到全量），
不再连续整篇读几十篇；只有个别需要正文时才读，且优先读头部。

## FIX-104 【大问题·用户发现】续派（非首次）仍注入**完整契约** ⇒ 常驻成员每轮重复吃一遍总纲/角色卡

  ② 同一份内容在上下文里出现多份，容易让成员对"哪份是最新"产生歧义
- 续派真正需要带的只有：**本轮任务切片**（任务号 + 上级补充指令 + 本轮范围 + 必要的路径/指针）

**要求**：
1. **续派（非首次）只注入增量**：消息 = 【本轮任务切片】+ 一句「角色卡、纪律、文档规范沿用本会话开头那份契约」；

   ② 首次创建**仍含**完整契约；③ 契约指纹变化后 → 续派带更新说明与变化段；④ 续派消息长度受**任务切片预算**约束
6. 预算口径（FIX-75）不变：任务切片软 1000 / 硬 2000 字

**验收**：真机对同一常驻角色连续派两次 → 第二次的消息只有任务切片（几百字量级），
不再重复总纲/角色卡；若期间插件升级导致契约变更，则第二次会明说"契约已更新"并只带变化段。

## FIX-109 【机制·用户提议】审计**新增**条目自动推送给馆员（增量推送 + 去重节流 + 按能力路由）

**用户原话**：「当审计增加时给官员（馆员）**自动推送**那条增加后的审计条目」。

**目标**：审计的价值在于"有人去修" —— 现在只到人眼前、靠上级转述（就会漏）。要做成：**新增条目 → 自动送到能干活的角色手上**。

**要求**：
1. **算增量**：每次审计算完（`audit_scan` / 面板强制刷新 / 启动自愈 / 快照同步任一入口 —— **同源**）后，
   与"上次已见条目集合"比对 ⇒ 得出**新增条目**。条目**指纹** = `check + target + detail`（内容不变即同一条）
2. **去重 + 节流**（不然会变成噪音）：
   - 同一条指纹**只推一次**；消失后再出现可再推
   - 一轮里的**多条新增合并成一条**推送（不要一条一条推）
   - 冷却时间（如 5 分钟）内不重复推；推送失败不重试轰炸（记入待推送池即可）
3. **推给谁（按能力路由）**：检查项 → 责任角色映射，**只推给能修的**：
   - 馆员（簿记）：`doc_misfiled` / `doc_kind_mismatch` / `legacy_caret` / `stray_non_md` / `missing_kind_index` /
     `null_frontmatter` / `doc_meta_missing` / `doc_tags_stale` / `missing_progressive_link` / `dirty_related_path` /
     `archive_suggest` / `occupancy_conflict`
   - 实现者/写档人：`over_budget`（文档超长）这类"要改正文或重写"的
   - 只给人（需裁定）：如"待人工裁定"类
4. **没有活跃馆员时不许丢**：进**待推送池**（持久化、幂等、可见）；下次给该角色的派单里**自动带上**
   （与 FIX-108 的"契约带审计摘要"接上 —— 那里带的就是"未处理的增量"）
5. **可关 + 可见**：配置开关（默认开）；`contract_status` 与面板显示「待推送 N 条 / 已推送 M 条 / 最近一条」
6. 断言：① 造新增条目 + 有活跃常驻馆员 → 收到**一条合并推送**（含条目与建议动作）；
   ② 无活跃馆员 → 进待推送池，下次派单契约里带上；③ 同一条不重复推；④ 关掉开关则不推；⑤ 增量与"审计全量"同源

**验收**：真机制造一个新审计项（例如往类别目录放个非 `.md`）→ 触发一次审计 → 馆员**收到一条推送**
（只含这条新增 + 建议动作）；再触发一次同样的审计 → **不再重复推**。

## FIX-112 【数据损失】`stripNullFrontMatter` 把"只有归档字段"的头也判成"全 null" ⇒ 整段删掉（归档标记丢失）
